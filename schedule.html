    I Built a Tiny Passkey Authenticator, Then Had to Explain Why You Shouldn’t Trust It

    George Coldham

    Identity and hardware security

    Abstract and bioHide details

    Abstract

    Passkeys promise a cleaner future: no shared secrets, less phishing, and fewer humans being blamed for typing passwords into convincing nonsense. But what actually makes a passkey secure?

    In this talk, I’ll use a small FIDO2 authenticator built on cheap microcontroller hardware to explore what is actually happening when a passkey is created and used. I’ll show the project, explain how it was put together, and use it as a practical way to examine where trust really lives in a passkey authenticator. Because a device can work perfectly and still be a terrible place to put your trust.

    We’ll look at the security boundaries around private key storage, firmware, physical access, hardware, supply chain and the assumptions we make about the authenticator itself. Because “phishing resistant” does not mean “magically secure”. Attendees will leave with a practical mental model for how passkeys work, why they resist phishing, and where the remaining security boundaries sit.

    For anyone who wants to build one themselves, I’ll provide the project resources and hardware details afterwards.

    Speaker

    George Coldham

    George Coldham is a Cloud Solution Architect in Security at Microsoft, based in Perth, Western Australia. He works with organisations on cloud security, identity, Zero Trust, securing AI systems, using AI for security, and practical security architecture.

    He is also the founder of the Global Security Community and an organiser of the Perth Microsoft Security Meetup and Global Security Bootcamp Perth. He regularly speaks about security topics that sit between enterprise reality and hands-on experimentation. His recent work has focused on passkeys, phishing resistance, browser security, agentic systems, and how security controls actually behave once humans and legacy assumptions get involved.

    George enjoys turning abstract security ideas into practical demonstrations, preferably with small devices, live demos, and just enough questionable hardware decisions to make the lessons memorable.

    Go Foot, Meet Gun: Auditing the Go Ecosystem for Its Sharpest Edges

    Zoltan Madarassy & Alex Brown (elttam)

    Code review

    Abstract and bioHide details

    Abstract

    Go is pretty safe by default — mostly — which is exactly why the subtler problems go unnoticed. This talk picks up where our two-part Golang code review notes blog posts left off, hunting for the footguns that slip past code review, the compiler, and your linter alike. We’ll walk through representative examples from each part of the blog series — such as ReverseProxy dropping auth headers when an attacker sets the right Connection value, and silent integer overflows that only misbehave on certain architectures — before turning to the broader set of standard-library and web-layer pitfalls the rules cover.

    We will then talk about how we used the Semgrep rules made during this research across a large slice of the most popular open-source Go projects on GitHub — the libraries and infrastructure much of the software supply chain quietly depends on. You’ll hear how the rules were written and tuned to survive real codebases, which footguns turned out to be widespread versus genuinely rare, and what that says about the gap between the language getting safer and anyone actually adopting the safer patterns. You’ll leave with the rules, the method to run them against your own dependencies, and a sharper eye for the Go patterns worth auditing by hand.

    Springing Cats Together: Chaining Intended Behaviours into RCE

    Chris Elliott

    Red teaming and exploitation

    Abstract and bioHide details

    Abstract

    You land on a Spring Boot Admin console managing hundreds of containers. The environment is heavily restricted: there is no file upload functionality, no writable web root, no log poisoning opportunities, and zero usable CVEs. So, how do you get a shell?

    This technical walkthrough dives deep into the internals of Java Spring and Tomcat to explore what happens when you are forced to rely entirely on first-principles thinking. Instead of hunting for traditional memory corruption bugs, this talk breaks down how these servers operate by design.

    By dissecting a highly predictable behavior in Tomcat’s internal mechanics and chaining it with exposed Jolokia JMX endpoints, we will explore how to turn expected server state into exploit primitives. Join this session to see how a perfectly timed race condition can weave intended features together into a reliable path for Remote Code Execution.

    Dumpster Diving for AI Agent Data Leaks

    Alexander Wilczek

    AI data leaks

    Abstract and bioHide details

    Abstract

    OpenClaw is the most popular AI agent framework of the year, with 390,000 GitHub stars. Install it, hand it your API keys, OAuth tokens, database credentials and private keys, and a single agent will run your email, calendars, shells, cloud accounts, messaging and payment tools for you. That is the appeal, and that is the problem. These agents only work well when they are over-privileged, so users grant everything and least privilege quietly disappears. Adoption was viral. Security was an afterthought.

    Early 2026 showed what that costs. ClawHavoc pushed over a thousand malicious skills into the OpenClaw marketplace, and an exposed Moltbook database leaked roughly 1.5 million API keys. The response focused on scanning skills before publication. Nobody was asking where the stolen data was ending up, so I went looking. To date I’ve identified close to 3,000 leaked secrets across nearly 1,400 breaches.

    The biggest pattern is OpenClaw leaking itself: Firebase and GCP keys embedded in agent JSON configs, gateway tokens committed as environment variables, session logs pushed to version control with auth tokens still intact, and SOUL.md personality files exposing the agent’s system prompt with credentials baked straight in. And because an agent never leaks just the AI parts of an .env file, everything else comes with it: AWS IAM keys, live Stripe keys, GitHub PATs, database connection strings, SSH private keys. On the exfil side I’ll cover Telegram bot exfiltration with the bot token embedded in the skill, a long tail of drop services, and hardcoded C2 ranges.

    Once the find rate held up I built BreachClaw, a free live hunter anyone can use to check their own exposure by email or by SHA-256 hashed secret. I’ll walk through what it has found so far, which types of keys leak most, and run a short live demo.

    I’ll close on reinstating least privilege. Agents need broad access to be useful, for now, so the practical move is to automate the things where a breach wouldn’t be catastrophic, treat every privilege you grant as a breach waiting to happen, stick to official skills, rotate credentials, and monitor the output side so you find out when something leaks rather than when someone uses it.

    Speaker

    Alexander Wilczek

    I’m a digital nomad fighting cybercrime. I’ve been travelling Australia (and the world) full time for over three years in my Land Cruiser and hacking the planet from the most pristine beaches to the most remote parts of the outback. I specialise in dark web, data leaks and cybercrime. I’ve presented my research at DEF CON and multiple BSides events. I’m also the proud founder of Rivanorth.

    History and critical reasoning

    Abstract and bioHide details

    Abstract

    Viral Vulnerabilities: Unpacking Copy.Fail and related Linux Kernel bugs

    Angus

    Linux kernel and vuln research

    Abstract and bioHide details

    Abstract

    Remember Copy.Fail (CVE-2026-31431), the Linux Kernel vulnerability that went viral earlier this year? If you missed it, here’s all you need to know: it was a local privilege escalation bug found by researchers at Theori; for the past 10 years, almost every kernel from every major distro was vulnerable; the bug was exploitable with a 732-byte Python script with 100% reliability; and over the weeks following disclosure, numerous variants were found. Of course, online discourse was fuelled by the fact that it was one of the first critical Linux kernel bugs found using AI.

    In this talk, I’ll break down what the Copy.Fail bug is, how it was exploited, discuss the variant vulnerabilities, and give my thoughts on the future of this bug class in general. The hype cycle may have now passed, but I think it’s still a very interesting bug, and taking the time to understand it properly can lead to interesting insights.

    Never looked at the Linux kernel before? Don’t worry – there is absolutely no code in this talk. I’ll be explaining all of the core concepts from the ground up, and every slide is filled with hand-drawn diagrams to help you understand what’s going on.

    Nobody’s Protocol: Attacking TACACS+ in 2026

    Matt Jones (elttam)

    Network and vuln research

    Abstract and bioHide details

    Abstract

    TACACS+ is 42 years old and almost nobody thinks about it, yet it is still how most telcos, ISPs and large enterprises authenticate admin logins across every router, switch and firewall they own. Last year’s CISA advisory on Salt Typhoon has them harvesting credentials straight off TACACS+ servers. This talk covers a pre-authentication format string vulnerability that sat for 25 years in the daemon behind a large share of those deployments, giving code execution as root, along with the trick that recovers the shared key first so you can get there without credentials.

    The rest is a case study in how software security works for critical services in 2026. The bug class was solved in 2001 and compilers have caught it for 20 years, none of which helps when nobody owns the code. Getting a fix out took several months of disclosure, across an archived project at Meta, a vendor who wasn’t answering, and Cisco PSIRT confirming the code hadn’t been theirs for decades.

    The enemy within: running untrusted code through AI workloads

    Kumar Soorya & Kaif Ahsan

    AI security

    Abstract and bioHide details

    Abstract

    AI agents are no longer just generating text; they’re writing code, executing it, installing dependencies, calling APIs, and operating inside your infrastructure with varying degrees of autonomy. Products like coding assistants, autonomous dev agents, and tool-calling LLMs need to run untrusted, dynamically generated code as a core part of their functionality.

    The AI workloads being non-deterministic means the user can manipulate the underlying system more easily and achieve a greater impact. Hence, it demands a fundamentally different approach to isolation.

    And when we think of isolation, the first thing that comes up is sandboxing. But the word “sandbox” is doing a dangerous amount of heavy lifting, and it hides an enormous amount of complexity. How does one properly “sandbox” an AI-native workload? What are the common trade-offs, mistakes and architectural best practices?

    This talk is a practitioner’s guide to getting sandboxing right for AI workloads, built from our experience building & securing AI products at Atlassian.

    We’ll do a practical walkthrough of building a AI sandbox: what are the major isolation layers, explain what the trust boundary actually is, showcase how we evaluated and selected solutions at each layer for our AI products, and then drive the point home with mock vulnerabilities representative of real bugs we’ve seen in the industry, while building our own products.

    You’ll see how a security & engineering team actually reasons through the complex challenges of sandboxing a non-deterministic workload. We’ll share the trade-offs we hit, the assumptions that broke, the actual vulnerabilities they caused, and the architectural decisions that survived contact with reality. So gather along and come hear our tale.
